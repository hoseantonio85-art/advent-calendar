## Открытые вопросы интеграции

- **Хост-приложение:** точка размещения известна **по скриншоту «ВтороеКрыло»** — под верхним рядом карточек перед основным названием экрана. Исходного репозитория Flutter нет на подключённом GitHub, версия и router неизвестны. Поэтому `AdventEntryCard` — переносимый компонент, **не изменённый APK**.
- **Прогресс:** текущий HTML использует `localStorage`; Flutter должен получить данные из согласованного источника **для полного календаря**, но не отображать их на входной карточке.
- **Часы:** `daysUntilNewYear` передаётся из хоста для единого правила кампании. Сам UI-кандидат не вычисляет дату, чтобы не вносить расходящиеся часовые зоны.
- **Лайки:** в актуальном MVP их нет. Старый `docs/likes-api.md` — архивное предложение, не обязательство к реализации.
- **Шрифты и графика:** источник графики согласуется при переносе; Yeseva One и Roboto должны быть зарегистрированы в нативном приложении, права на ресурсы проверены.

**Актуализировано:** 24 ноября 2026  
**Главный принцип:** один утверждённый календарь, без альтернативных тем в продукте.  
**Действующая демоверсия:** https://hoseantonio85-art.github.io/advent-calendar/  
**Источник UX/UI:** `index.html` в `main`.

## Решение от 22 ноября 2026: UX/UI завершён

**Завершён именно этап дизайна**, а не реализация продукта: согласованы основной календарь (Midnight Forest), карточка входа v9, состояния дат и bottom sheet. До отдельного требования UI не переделываем. Последующие UX-замечания оформляем как новые задачи, не возвращая исторические визуальные альтернативы.

**Следующий утверждённый порядок:** #3 единые данные, правила и архитектура → #2 автономный нативный Flutter-календарь → #4 платформенные адаптеры/хранение (часть можно вести параллельно с #2) → #1 подключение входной карточки и Flutter QA → интеграция в приложение и общий выпуск. Flutter разработку можно начинать **без доступа к исходникам хоста** на собственном демо-приложении; только реальное встраивание зависит от «ВторогоКрыла».

**Техническое описание:** [TECHNICAL-PLAN.md](TECHNICAL-PLAN.md) — границы независимого модуля, контент, часы, прогресс, возможный backend, критерии готовности и открытые решения. Серверная синхронизация — **опция по требованиям**, а не автоматически обязательный этап.

## Открытые вопросы интеграции

- **Хост-приложение:** точка размещения известна **по скриншоту «ВтороеКрыло»** — под верхним рядом карточек перед основным названием экрана. Исходного репозитория Flutter нет на подключённом GitHub, версия и router неизвестны. Поэтому `AdventEntryCard` — переносимый компонент, **не изменённый APK**.
- **Прогресс:** текущий HTML использует `localStorage`; Flutter должен получить данные из согласованного источника **для полного календаря**, но не отображать их на входной карточке.
- **Часы:** `daysUntilNewYear` передаётся из хоста для единого правила кампании. Сам UI-кандидат не вычисляет дату, чтобы не вносить расходящиеся часовые зоны.
- **Лайки:** в актуальном MVP их нет. Старый `docs/likes-api.md` — архивное предложение, не обязательство к реализации.
- **Шрифты и графика:** источник графики согласуется при переносе; Yeseva One и Roboto должны быть зарегистрированы в нативном приложении, права на ресурсы проверены.

## Запреты для финальной сборки

- Не брать в приложение архивные варианты `versions/`, `winter-glass/`, `compare.html` (они уже удалены из `main`).
