# Физический Android: воспроизводимая QA и профиль

Телефон к рабочей среде Codex не подключён. **Физическая проверка не выполнена.** Debug-эмулятор подтверждает функциональные сценарии/отсутствие ошибок, но не производительность телефона. Дизайн при этой проверке не пересогласовывается.

## Подготовка

- ARM64 Android, отвечающий minSdk из release-manifest отчёта. Записать модель/Android/RAM, частоту дисплея, renderer, настройки шрифта и reduced motion, температуру/энергосбережение.
- Основной APK — **test release ARM64**, debuggable=false, с тестовой подписью и applicationId demo. Это не production и не магазинный выпуск.
- Profile ARM64 — отдельный диагностический APK. Release/Profile одного прогона имеют одну тестовую debug-подпись. Старое demo из иного CI может иметь другую; не удалять приложение с ценными локальными данными без учёта их потери. Реального хоста эти APK не касаются.
- Для ручной приёмки установить test release; для замеров — profile. Точные ссылки/commit/размер/сертификат сохраняются в техническом отчёте и Releases.

## Ручная функциональная матрица release

| Сценарий | Ожидаемый результат |
|---|---|
| Вход → календарь → день → назад | Полный маршрут; сначала закрывается шторка, потом календарь |
| Будущее обычное мероприятие | Открывается сейчас; просмотр хранится, прогресс не растёт до даты |
| Московская дата наступила / resume | Ранний просмотр начислен без повторного открытия |
| Пропущенный совет | Доступен, повторное открытие не увеличивает счётчик |
| Будущий совет/сюрприз | Только уведомление, без открытия/начисления |
| Сюрприз после 00:00 Москвы | Доступен; конфетти один раз, включая перезапуск |
| Избранное добавить/удалить | Состояние и история согласованы после перезапуска |
| Share → отправка/отмена | Системный chooser; отмена не выглядит ошибкой |
| Add to Calendar | Подтверждение source/allDay → редактор ОС; не заявлять сохранение по факту запуска |
| Нет календаря/отказ/ошибка ОС | Внятный unavailable/error, кнопка остаётся доступной для повтора |
| Back/drag/close | Жесты и закрытие не блокируются при повторениях |
| 80/100/150/200%, safe areas, reduced motion | Нет ошибок layout; 4/2 плитки отсчёта; согласованное движение сохранено |

Нельзя добавлять переключатель виртуальной даты в пользовательский APK. Даты/полночь/одноразовые claims автоматически проверены тестами с внедрёнными часами; для проверки на телефоне использовать отдельный интеграционный target из исходников или системную дату тестового устройства. После эксперимента восстановить автоматические дату/время; реальные события календаря создавать только осознанно.

## DevTools profile

С той же версией Flutter и исходниками проверенного commit:

```text
flutter devices
cd flutter/example
flutter run --profile -d <physical-id> --target=lib/main.dart
```

Либо установить выданный profile APK и подключиться `flutter attach --profile -d <physical-id>`. Проверить, что инструмент действительно пишет PROFILE и выбран физический device. Отчёт снять в DevTools Performance; экспортировать timeline. Фрейм-бюджет брать из реальных 60/90/120 Hz, не объявлять любой кадр <16.7ms достаточным на 120 Hz.

Сначала холодный запуск, затем прогрев 5–10 секунд; записать оба. По отдельности: 20 секунд прокрутки вниз/вверх, 20 открытий/закрытий шторок, drag-to-dismiss, 15 секунд истории со стеклом/живым секундным счётчиком, 15 секунд неподвижного календаря со снегом/звёздами/текущей датой. Повторить с reduced motion и крупным шрифтом. В отчёте — frame count, build/raster p50/p90/p95/p99, худший кадр, доля превышения бюджета; не смешивать first shader/image decode и steady-state.

В DevTools Memory и `adb shell dumpsys meminfo com.example.advent_demo` записать память после прогрева, 20/50/100 открытий и минуты покоя; при доступности инструмента отдельно после GC. RSS включает engine/decoded images/raster cache, поэтому единичный рост и maxRSS **не доказывают** утечку. Проверять устойчивый рост после повторных циклов/GC, controllers/listeners и retain paths. Следить, что статическая фотография не перезаписывается при каждом тике; этот контракт уже имеет widget-тест.

## Автоматический physical profile target

```text
flutter drive --profile -d <physical-id> --driver=test_driver/integration_test.dart --target=integration_test/stability_profile_test.dart
```

Только физический Android PROFILE. Target использует отдельные in-memory fixtures и движущиеся часы тестовой даты, не является entrypoint пользовательского APK. Сохраняет raw FrameTiming по фазам scroll/idle/sheets/history и RSS в `build/android-motion/timings.json`. Этот target подготовлен и статически анализируется CI, **на телефоне Codex его не запускал**. Полный DevTools timeline и 50/100 циклов остаются ручной частью процедуры.

Результаты сохранять в GitHub с commit, APK checksum, устройством и файлами trace/memory; только затем решать, есть ли реальная проблема и нужна ли техническая оптимизация. Не менять графику, размеры или согласованные анимации ради условного FPS/веса.
